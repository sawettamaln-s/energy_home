# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Energy Home: a Flutter app (thesis/education project) for tracking household electricity and water costs in Thailand per billing cycle. The user sets a billing day and enters the meter reading from their latest bill (the cycle's start reading), then records readings during the cycle. The app estimates costs with real MEA/PEA (electricity) and MWA/PWA (water) tariffs, including TOU meters (On-Peak/Off-Peak), forecasts the cycle total and next month, and compares against past bills. Backend is Firebase (Auth + Firestore).

## Conventions

- Code comments, UI strings and docs are in Thai. Comments describe current behavior only, with no history ("เดิมเป็น X เปลี่ยนเป็น Y").
- UI text is polite Thai ending in "ค่ะ". Use one term per concept: วันตัดรอบบิล (billing day), เลขมิเตอร์ต้นรอบ (cycle start reading), บิลย้อนหลัง (past bills); both live on the settings page "เลขมิเตอร์จากใบแจ้งหนี้", รายจ่ายประจำ (fixed costs), สิ้นรอบบิล (end of cycle, not "สิ้นเดือน").
- Colors live only in `lib/styles/app_colors.dart` (`AppColors`, mirrored by `DashboardStyles`). Don't hardcode new `Color(0x...)` values in screens. Material `Colors.grey.shadeN` etc. are fine. Electricity/water accents use `AppColors.electricityBorder`/`waterBorder`; warning boxes use `AppColors.warning` (background alpha), `warningIcon`, `warningText`, `warningBorder`. In history tables, closed cycles (meter-log history) and past years (invoice page) use `AppColors.closedSurface` with `closedBorder`; the current cycle/year stays white. Info buttons use `Icons.info_outline`.
- Changes that alter app behavior, data or flow get confirmed with the user before they're made.

## Commands

```bash
flutter pub get
flutter run
flutter analyze                        # lint (flutter_lints; platform dirs excluded)
flutter test                           # all tests, no real Firebase needed
flutter test test/record_meter_screen_test.dart                       # single file
flutter test test/fixed_cost_item_test.dart --plain-name "<test name>"   # single test
```

**Firebase config:** `lib/firebase_options.dart` is gitignored. For a build or analysis without a real project, copy `lib/firebase_options.sample.dart` to `lib/firebase_options.dart` (CI does this). Use `flutterfire configure` for a real project.

**Firestore rules tests** (`test/firestore_rules/`, not in CI or `flutter test`): `cd test/firestore_rules && npm install && npm test` runs them on the Firestore emulator (needs Node, Firebase CLI and Java 21+). Run them after any change to `firestore.rules` or to the fields the app writes. Deploy the rules with `firebase deploy --only firestore:rules`.

CI (`.github/workflows/flutter-ci.yml`) runs `flutter analyze` and then `flutter test` on pushes and PRs to `master`.

## Architecture

- **Startup:** `main.dart` initializes Firebase and `NotificationService`, clamps the system text scale to 0.85–1.3, and opens `AuthGate`. `AuthGate` listens to `authStateChanges` and routes to `WelcomeScreen`, `SetupScreen` (only when the user doc doesn't exist; a load error shows a retry screen instead, so the doc is never overwritten) or `MainShell`. It's keyed by uid so switching accounts reloads the data. To log out, push a fresh `AuthGate()` with `pushAndRemoveUntil`.
- **New-user flow:** `SetupScreen` asks only for area and meter type. The dashboard then shows a 3-step checklist (billing day → meter reading from the bill → optional past bills) until a start reading exists, and an onboarding dialog on first visit.
- **`MainShell`** keeps all 4 tabs (dashboard, analysis, appliance, settings) alive in a single `IndexedStack`, so `initState` does not run again when the user switches tabs. The bottom bar (`AppBottomNavBar`) lives once in `MainShell`, so its selected pill can slide between tabs; the four screens show their own bar only when opened outside the shell (`onNavTap == null`), so don't add one back to a screen's `Scaffold`. Cross-tab refresh goes through **`DataRefreshBus`** (`lib/utils/data_refresh_bus.dart`): `FirestoreService` calls `notifyChanged()` after writes/deletes of the user doc, bills, logs and start readings, and `DashboardScreen`/`AnalysisScreen` listen to `DataRefreshBus.instance.version`. Appliances are not on the bus; their screens listen to the Firestore stream (`getAppliances`). A new write method other screens depend on has to call `notifyChanged()`.
- **`FirestoreService`** (`lib/services/firestore_service.dart`) is the only Firestore access layer. User data lives under `users/{uid}` with the subcollections `bills`, `appliances`, `electricity_logs`, `water_logs`, `fixed_costs` and `start_meter_history`. The Ft rate is in `app_config/electricity_rates`, read-only from the client (see `firestore.rules`). The rules also check each collection's field types and ranges (numbers non-negative, enums such as `area`/`source`, `id`/`uid` matching the path), only for the fields a write changes, and deny any other subcollection, so a new field or collection needs a rule change too. The service accepts an injected `FirebaseFirestore`, and `AuthGate`/auth screens accept an injected `FirebaseAuth`. Tests use `FakeFirebaseFirestore` and `MockFirebaseAuth` (plus `mock_exceptions` to simulate `FirebaseAuthException`). Keep new Firebase-touching code injectable. `DashboardScreen` accepts a `DashboardLoader` and a `FirebaseAuth` (see `test/dashboard_screen_test.dart`). `AnalysisScreen` accepts an `AnalysisService` (itself built on an injected `FirebaseFirestore`), a `FirestoreService` and a `FirebaseAuth` (see `test/analysis_screen_test.dart`). `ApplianceScreen` and `SettingsScreen` accept a `FirestoreService` and a `FirebaseAuth` (see `test/appliance_screen_test.dart`, `test/settings_screen_test.dart`).
- **Settings** (`lib/screens/settings/`): `settings_screen.dart` is one library split into `part` files by feature (start-meter form, past-bill form, invoice page, billing-day dialog, tariff, account deletion, fixed costs, rate page, meter-log history), so private names are shared across them. `settings_invoices.dart` (`InvoiceScreen`, opened by `openInvoiceScreen`) is the one place for invoices (titled "เลขมิเตอร์จากใบแจ้งหนี้"): a latest-invoice card (start reading, `_AddStartMeterSheet`), a บิลย้อนหลัง section (`_AddHistoricalBillSheet`; a full card only before the latest invoice is entered or when months are missing, otherwise one line with an add button) and a month table that joins bills of every source with `start_meter_history` records on the same year/month (an invoice's month is the month the next cycle starts, so a record and its `'startMeter'` bill share it), with labelled ประเภท (ไฟฟ้า/น้ำ) and แสดง (ยอดเงิน/เลขมิเตอร์) filters; tapping a row picks the right form. Old start readings can't be edited (the next cycle's units depend on them), only deleted per utility. Missing months and the dashboard backfill reach back to `StartMeterRecordModel.trackingStartKey` (the oldest start record), not `startBillingMonth`, which is overwritten with every new invoice. Both cost-entry forms use `_CostAutofill` (`settings_cost_autofill.dart`) to price typed units. Re-pricing the current cycle's logs after a start-reading edit lives in `FirestoreService.recalcCurrentCycleLogs` (one batch, one refresh). A `'startMeter'` bill's `fixedCost`/`totalCost` use the fixed costs active in its bill month, like the other sources.
- **Billing-cycle rules** (break these and the dashboard/analysis go wrong):
  - Cycle boundaries come only from `EnergyForecaster` (`lib/utils/forecaster.dart`). The billing day is the *first* day of the new cycle.
  - A bill's `year`/`month` is the cycle's *closing* month (the invoice month). A `start_meter_history` record's `billingMonth` is the month the cycle *started*. Editing the current cycle's start reading overwrites its record.
  - Log `cost`/`usedFromStart` are cumulative from the cycle start. For TOU, `meterValue` stores units used since the cycle start; the real readings are `peakMeterValue`/`offPeakMeterValue`.
- **Dashboard** (`lib/screens/dashboard/`): `dashboard_screen.dart` only lays out cards (in `widgets/`) and navigates. All data work is in `DashboardLoader` (`dashboard_loader.dart`): `load()` fetches only what the screen shows (in parallel) and returns an immutable `DashboardData` (costs, meter-card readiness, stale-cycle message, and the end-of-cycle forecast used only by the forecast notification); `runBackgroundTasks()` then does the fixed-cost recalc, bill compilation/backfill, tariff hint and notification checks, and returns the unread count and any new tariff hint for the screen to show. Overlapping loads are queued, and a reload keeps the old content on screen. The fixed cost shown is the one for the current bill month (same rule as `compileBill`), not `user.fixedCost`. The dashboard shows only actual figures (the app is a usage tracker); the end-of-cycle forecast lives on the analysis tab, and a chip on the hero card links there. When the hero card has no amount to show (`HeroPending`: a new user, or a new cycle whose start reading isn't set yet so both meter cards are locked), it says so instead of showing 0.00 and hides the cycle bar; new users also get the app flow (`SetupFlowStrip`) and a `TariffFactCard` below the fixed costs with their real price-per-unit tiers, the current Ft and a link to the rate page (`widgets/starter_visuals.dart`). The unit-to-cost calculator (`lib/widgets/quick_cost_sheet.dart`, built on the `TariffTables.*Parts` breakdowns) opens only from the calculator icon in the dashboard header; it starts from the user's area, meter type and tariff, and the sheet can switch them to price another home without saving anything. It also works backwards: a baht amount gives the most whole units it buys (`TariffTables.unitsForBudget`; TOU shows the range from all On-Peak to all Off-Peak).
- **Bill compilation:** on each dashboard load, `compileBill()` turns the just-closed cycle's logs into a `'compiled'` bill (and backfills missed cycles back to `startBillingMonth`). Bill sources are `'compiled'`, `'imported'` (past bills entered by the user) and `'startMeter'` (created with a start reading; editable only from that page).
  - Totals start from the cycle's latest log and are projected to the cycle end with `cycle_projection.dart` (the same projection as the "current cycle" forecast). A `'startMeter'` bill for the same month later overwrites it with invoice figures. The invoice page lists all three sources; compiled bills there can be edited (saved as `'imported'`) but not deleted.
  - The fixed cost is recomputed for that cycle's month (`isActiveInMonth`). It does not come from the `user.fixedCost` cache, which only holds the current month's value.
  - TOU peak/off-peak usage is subtracted from the start record of the month the compiled cycle started, not from the user's current start values.
  - `compileBill()` returns a `CompileBillResult` (`created`/`noLogs`/`failed`) and never throws. The backfill flags a cycle as missed (and notifies) only on `noLogs`; on `failed` it stops and retries on the next load.
  - `tool/migrate_tou_bills.dart` (standalone, not in the app) repairs compiled TOU bills whose On/Off-Peak units are 0 by chaining the closing logs of each cycle.
- **Meter entry rules** (`lib/utils/meter_reading_check.dart`, used by `record_meter_screen.dart`): a reading must not be below the cycle start reading or the latest reading of the current cycle (TOU checks each field). Invalid input disables the save button and shows a fix shortcut (start-meter setup or the meter-log history).
- **Notifications** (`NotificationService`, singleton): toggles, history and de-dup keys are stored in SharedPreferences, scoped per uid (`uidProvider` can be overridden in tests). Instant checks run from `DashboardLoader.runBackgroundTasks`, which catches its own errors. The billing reminder is scheduled for 09:00 on the billing day. `syncDeliveredScheduledNotifications()` must run before `scheduleBillingReminder()`, or a delivered reminder never reaches the history. Sign-out and account deletion call `cancelScheduledForSignOut()` first (the keys are scoped to the current uid), or the device keeps reminding for the old account. Tapping a `spike`/`forecast` notification opens the analysis tab via `NotificationScreen.onOpenAnalysis`. When the Ft doc changes (rate or `ft_effective_from`), `notifyFtChanged` (under the `summary` toggle) tells the user; it reads Ft through `FirestoreService.getFtInfo()`, which returns null on errors, and the first value it sees is only remembered.
- **Pure logic in `lib/utils/`** (no Firebase or widgets, so it's easy to test):
  - `tariff_tables.dart` (`TariffTables`): the only copy of the tariff tables (tiers as `(upTo, rate)` lists), service fees, VAT and the cost formulas. Each formula has a `*Parts` version returning a `CostBreakdown` (energy, Ft, service fee, raw water, VAT, total); the plain versions return its total. Pure Dart, so the app, the rate page (which builds its table rows from these lists) and `tool/` scripts all import it.
  - `calculator.dart` (`EnergyCalculator`): binds `TariffTables` to the user's tariff and the Ft rate. Only `getFtInfo()`/`getFtRate()` touch Firestore: the value is cached for `ftCacheDuration` (10 min; failures aren't cached), `DashboardLoader` refreshes it via `rememberFtInfo`, and tests swap the source with `ftDocLoader` and call `resetFtSource()`. A zero-unit reading still costs the monthly service fee + VAT, as on a real bill. `calculateUsed` never returns a negative value. Rates were checked on 2026-10-08 (links at the top of the file): residential progressive electricity rates (1.1/1.2, 1.1.1/1.1.2) are the new ones effective from the September 2026 (2569) bill, taken from the PEA press release because the ERC tariff page still shows the old table; TOU and service fees didn't change; residential water has no minimum charge, and PWA uses table 3. The Ft rate lives in `app_config/electricity_rates` (`ft_rate`, optional `ft_effective_from` ISO date) and must be updated by hand every 4 months (Jan/May/Sep). Only Ft lives in Firebase: VAT (7%) and all tariff tables are constants in `tariff_tables.dart`, so changing them means a code change and a new release; the rate page warns when the period is over 4 months old. Normal meters take a `tariff` (`UserModel.electricityTariff`: `standard` = >150 units, `small` = ≤150 units). The invoice code differs by utility (MEA 1.1/1.2, TOU 1.3.2; PEA 1.1.1/1.1.2, TOU 1.2.2), so UI text must use `tariffCode`/`touCode`, never a hardcoded code; every cost calculation for a normal meter must pass the user's tariff. `FirestoreService.setElectricityTariff` re-prices the current cycle's logs and never touches closed bills. `tariff_advisor.dart` suggests checking the tariff after 3 consecutive bills at ≤150 (or >150) units, counting only bills whose units come from real readings (not `'compiled'`); the app never switches it on its own. The first time a hint appears, the dashboard shows `showTariffHintPopup` (settings_tariff.dart) with a button to the tariff picker; the system notification sits under the `summary` toggle.
  - `forecaster.dart` (`EnergyForecaster`): cycle boundaries, the end-of-cycle unit projection from the daily rate (`projectToCycleEnd`; early in the cycle the rate is blended with the previous cycle's bill per-day units, weighted as `priorWeightDays` = 5 extra days, and the dashboard, analysis card and `compileBill` all pass the same prior bill from `getBillForMonth`), the seasonal next-month forecast (the latest `seasonalRecentMonths` = 1 bill, deseasonalized, times the target month's factor; 1 month beat 2–6 on Thai statistics and RECON-SL bills), and the linear regression fallback used when area/meterType are unknown. The analysis tab forecasts next-month *units* and prices them (`AnalysisService.forecastCostFromUnits`, Ft read once per load); never apply the seasonal factor to a cost.
  - `cycle_projection.dart`: end-of-cycle forecast used by the dashboard's forecast notification, the analysis current-cycle card and `compileBill`. It projects *units* (TOU: On/Off-Peak separately) and prices them with `EnergyCalculator`. Never scale the cumulative cost by days: the service fee and the water minimum charge don't grow with usage.
  - `appliance_rate.dart` (`ApplianceRate`): the baht/unit rate for appliance estimates = electricity cost ÷ units of the latest usable bill, falling back to 4.5. The appliance screen and its form use this rate.
  - `appliance_energy.dart` (`ApplianceEnergy`): appliance kWh with the standard calculator formula (watt × hours ÷ 1,000) for every type, used by the appliance list and form; the appliance feature is a supplementary calculator like common web calculators. For fridges/air conditioners the form only advises entering the hours the compressor actually runs. `typeKey` gives an appliance's type: its `iconKey`, else an exact name match in `DefaultAppliances`. The appliance page leads with the top appliance; the all-appliance total is secondary because users rarely list every appliance. The analysis page has only electricity/water tabs; its "ดูอุปกรณ์ที่ใช้ไฟมากสุด" insight button switches to the appliance tab of `MainShell`.
  - `daily_usage.dart` (`DailyUsage.spread`): turns a cycle's cumulative logs into per-day units for the dashboard's daily chart; units between two readings are spread evenly over the days in between.
  - `seasonal_curves.dart` is **generated** from real monthly residential statistics (EPPO residential electricity for MEA/PEA, MWA residential water for Bangkok, PWA total water sold for upcountry — PWA publishes no residential split). Don't edit it by hand. Regenerate it with `python tool/seasonal_curves/build_seasonal_curves.py` (add `--fetch` to re-download the source data).
- **Styling:** `lib/styles/` holds colors, typography (`AppTypography.sN`), spacing (`AppSpacing.vN`) and `app_theme.dart` (`AppTheme.light()`: Material 3 theme with the bundled IBM Plex Sans Thai font in `assets/fonts/`, OFL; component themes for buttons, inputs, dialogs, bottom sheets, snackbars, tabs; radius tokens `radiusSm/Md/Lg/Xl`). Shared redesign components live in `lib/widgets/ui/`: `AppCard`, `IconBadge`, `AnimatedAmount` (count-up numbers), `FadeSlideIn` (one-time entrance animation). The logo images are in `assets/images/` (`logo_mark.png` green, `logo_mark_white.png` white, shown by `AuthLogo`); the app icons are generated from `assets/icon/` with `dart run flutter_launcher_icons` (config in `pubspec.yaml`), and after running it, revert its change to `ios/Runner.xcodeproj/project.pbxproj` (the tool rewrites an unrelated build setting). No emoji in UI text; use Material icons. `responsive.dart` provides `context.rf()`/`context.rs()`, which scale against a 375px base width. `DashboardStyles` (exported with all style files) holds shared text styles and card decorations.

## Tools (`tool/`)

Standalone scripts, not part of the app. Scripts that write to Firestore are dry runs until `--apply` is passed. They can't import `calculator.dart` (it depends on `cloud_firestore`), so they import the pure `tariff_tables.dart`/`forecaster.dart` instead of copying formulas.
- `seasonal_curves/` (Python): `build_seasonal_curves.py` builds the seasonal curves; `backtest_forecast_methods.py` reports MAPE of the forecast methods on the same real data.
- `backtest_forecast.dart`: walk-forward backtest of the app's forecast functions on one account's real bills.
- `backtest_cycle_projection.dart` (core in `cycle_backtest/`, tested by `test/cycle_backtest_test.dart`): read-only backtest of the end-of-cycle projection on one account. Ground truth is the next cycle's start reading minus this one's; it projects at days 3–25 with `projectToCycleEnd` (its `priorWeight` parameter lets the script try several prior weights), reports MAPE/MAE/bias, the best prior weight and a leave-one-cycle-out cross-validation.
- `backtest_seasonal_personal.dart` (core in `seasonal_backtest/`): next-month forecast experiments on RECON-SL monthly bills with a 5-fold split by household. Blending a household's own seasonal curve into the national one barely helped (best 15.6% vs 15.8% MAPE), so the app doesn't do it; the recent-bill window was tuned there and on Thai statistics.
- `backtest_cycle_dataset.dart`: the same backtest on the public RECON-SL smart-meter dataset (Sri Lanka, CC BY 4.0; prepare it with `cycle_backtest/prepare_recon_sl.py`, which drops solar-export homes). Cycles come from real cumulative meter readings; only billing days and the reading schedule (20:00 every 1–3 days, 20% skipped) are simulated, and cycles outside 20–1,500 kWh are dropped. It reports MAPE/WAPE and a 5-fold cross-validation split by household; `priorWeightDays` = 5 was chosen from it.
- `demo_data/generate_demo_account.dart` fills an existing account with demo data for one of the 4 cases (`bangkok_normal`, `bangkok_tou`, `upcountry_normal`, `upcountry_tou`) using the app's own cycle rules and seasonal curves. `--reset` clears the account's data first.
- `migrate_tou_bills.dart`: see `tool/README_migrate_tou_bills.md`.
- `list_bills.dart`: read-only listing of one account's bills.
